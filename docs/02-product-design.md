# 产品设计：GPU 值班员（暂名 `gpulease`）

> 一句话：一块 Windows 机器上跑着十来个 `python.exe`，你只想知道「现在在干什么、还活着吗、要不要人管」。
> 这不是监控工具，这是一个会说话的调度台。**只做 Windows。**

---

## 1. 产品命题

### 1.1 用户真正的问题只有三个

| 用户会问 | 现在的答案 | 我们给的答案 |
|---|---|---|
| 这张卡现在是给谁干活的？ | 任务管理器里一堆 `python.exe`，pid 对不上任何东西 | `训练 SDXL LoRA · 正常 · 已跑 1h 12m` |
| 它还在正常推进吗？ | 要人去翻日志、看 loss、看 nvidia-smi | `正常，最后输出 4 秒前` |
| 出事了我怎么知道？ | 出事之后才发现，晚上睡觉跑废了 6 小时 | 托盘气泡 / 推送：`20:41「训练 SDXL LoRA」已经 22 分钟没有输出了` |

### 1.2 为什么不是又一个 nvidia-smi 皮肤

已有的监控（nvitop / gpustat / 任务管理器 GPU 列）解决的是**数值可见性**：利用率多少、显存多少、温度多少。
但用户看到的是一张卡 + 一堆 pid。**数值过剩，语义为零。**

真正的缺口在两层：

1. **归属层**：pid → 人话任务名。需要调度器自己持有进程生命周期（spawn 时注入 `GPULEASE_RUN_ID`）。
2. **判定层**：把时序数值压成一个结论（正常 / 变慢 / 卡住 / 失败 / 丢失），再用一句人话说出来，并决定要不要叫醒人。

**这是产品壁垒，不是 UI 壁垒。** 竞品都能把数字画得更好看，但没人愿意为"更好看的数字"付钱；"半夜别白跑"是愿意付钱的。

### 1.3 不做的事（明确排除）

- **不做 Linux / WSL2 / 容器 / 多机**：产物是 `bun-windows-x64` 单 exe，没有第二套采集实现。SLURM、SkyPilot、k8s 一律不做——那是集群编排，不是单机值班。
- 不画 GPU 历史曲线（不存采样，见 `03-architecture.md` §6）。
- 不替代 TensorBoard / wandb（只读它们产出的日志，不重做实验跟踪）。
- 不自动杀进程、不自动抢卡（只报告 + 建议；自动调度是 v0.5，需要用户先建立信任）。
- 不碰集显 / 非 NVIDIA 卡：只认 `nvidia-smi` 枚举得到的卡，集显不参与判定。

## 2. 用户与场景

### 2.1 三类人，同一台机器

| 角色 | 场景 | 他关心的 |
|---|---|---|
| 单机炼丹的开发者 | 一张 4090 + 一张 3060，白天训练晚上生图 | 别互相挤爆显存；训练挂了要知道 |
| 小团队共用工作站 | 3 个人 RDP 上来跑任务 | 现在谁在占卡、哪个任务死了 |
| 生图/生视频批量跑 | ComfyUI 队列几百张，跑一整夜 | 卡死没有、出图失败率 |

三类人的共同点：**卡不是问题，卡上的黑盒才是问题。**
"3 个人 RDP 上来"这条决定了归属必须诚实：别人的进程我们只能看见 exe 名，看不见命令行。

### 2.2 典型痛点，按真实频率排序

1. 训练 OOM 静默退出，人在睡觉（最贵）
2. 两个任务抢同一张卡，互相把对方挤 OOM
3. ComfyUI 卡在某个节点不动，但进程还在、显存还占着（"空占用"）
4. 外接显卡拔了/驱动崩了，任务全死，没人知道为什么
5. 想知道"还要多久"，只能靠眼睛估

## 3. 核心概念

```
GPU ×N（同一台 Windows）
  └─ Task（任务）── Run（一次执行）
        ├─ Progress（进度快照，v0.2）
        ├─ Verdict（健康判定）── Alert（通知，v0.2）
        └─ Logs（日志尾部）
```

| 概念 | 定义 | 为什么要它 |
|---|---|---|
| **Task** | 用户视角的最小单位，有**自然语言名字**（"训练 SDXL LoRA"） | 这是产品的主角，不是 GPU |
| **Run** | 一次执行（重启 = 新 run），记 pid 树、退出码、日志路径 | 断联重跑后能说"这是第 2 次尝试" |
| **Verdict** | 规则引擎的结论：7 个状态之一 + 一句人话 | 产品的核心资产 |
| **Progress** | `{phase, done, total, unit, rate, eta}` 的统一结构 | v0.2 的适配器层，v0.1 没有 |
| **Alert** | 需要人处理的 Verdict，带去重和静默窗口 | v0.2 |
| **Lease** | 任务对某张卡的独占占用权 | v0.5；v0.1 用 `--gpu` 设 `CUDA_VISIBLE_DEVICES`，不做租约 |

v0.1 落地的只有 Task / Run / Verdict / Logs 四项；其余标注版本，不假装已有。

### 3.1 任务来源：先做能保证正确的那个

| 来源 | 归属精度 | 状态 | 怎么做 |
|---|---|---|---|
| **托管启动** | 精确 | **v0.1 已实现** | `gpulease run --name "训练 SDXL" --gpu 0 -- python train.py`，pid 是自己 spawn 的 |
| **只读发现** | 低 | **v0.1 已实现** | 外部进程只显示 `python.exe · 非本机托管`，计入 `external` 数，不猜归属 |
| **纳入管理**（attach） | 高 | v0.3 计划 | `gpulease attach <pid> --name "..."`；退出码和 stdout 拿不到，只能靠日志活跃度判 |

**关键设计**：托管启动时注入 `GPULEASE_RUN_ID` / `GPULEASE_TASK_ID` / `GPULEASE_RUN_NAME`，子进程树全部可追溯；任务退出后由 supervise 进程捕获退出码、回收日志、落库。这比轮询 `nvidia-smi` 猜 pid 可靠一个数量级。
不读子进程的环境变量（Windows 上读别人的环境要管理员权限），只认我们自己记下的 pid 集合。

### 3.2 Windows 硬限制（直接改写了规则设计）

**拿不到「每个进程用了多少显存」。** WDDM 驱动模型下显存由内核统一管理，NVIDIA 驱动不知道单进程占用：`nvidia-smi --query-compute-apps=used_memory` 在 Windows 消费卡上**恒为 N/A**（提示语是 "Not available in WDDM driver model"）。任务管理器的「专用 GPU 内存」列能人工看，但程序化路径（GPU Process Memory 计数器）有微软官方记录的读数不准问题。

| 能拿到 | 拿不到 |
|---|---|
| pid、exe 名、整卡 `memory.used/total`、利用率、温度、功耗 | per-process 显存；pid 对应的卡号（`--query-compute-apps` 不返回 `gpu_uuid`） |
| 我们自己 spawn 的进程的 pid 树与退出码 | 其他用户 / 提权进程的命令行（`Win32_Process.CommandLine` 为 `NULL`） |

后果：

- 任务级判定只用**进程存活 + 输出活跃度**；显存只在卡级说。
- 播报里不出现「你的任务占了 18.2G」，只出现「卡 0 显存已满」。**这不是妥协，是正确性。**
- v0.1 不回答"这个任务在哪张卡上"，按卡归属留到 v0.2（`gpuIndexOf()` 现在恒为 `null`，见 `src/state.ts`）。

另外两条 Windows 事实：**没有 Xid**（那是 Linux 内核 NVRM 的概念），等价物是 `nvlddmkm` 事件与 TDR（事件 4101）；**DCGM 官方只支持 Linux**，所以健康判定只能来自 `nvidia-smi` + 事件日志，这也正好让"零依赖"成立。

## 4. 自然语言播报（产品的脸）

### 4.1 三种粒度

**任务行**（面板主体，一行一个任务）：
```
● 训练 SDXL LoRA   正常    已跑 1h 12m   最后输出 4s 前
```
**卡片**（顶部每卡一行，永远只有 4 个数字）：
```
卡0 RTX 4090  62%  18.2/24.0 GB  71°C
```
**播报**（异常时的一句话，也是推送正文）：
```
20:41「训练 SDXL LoRA」已经 22 分钟没有输出了，进程还在。看一眼日志尾部。
```

### 4.2 播报生成原则

- **模板生成，不调 LLM**：离线、免费、确定、0 延迟。规则 → 句子片段 → 拼装。
- **一句话里必须有**：时间、任务名、现象、可执行的下一步。
- **不做形容词**：不写"运行良好"，写"最后输出 4 秒前"。
- **异常优先于全面**：正常时少说话，异常时立即说。

### 4.3 健康判定规则表（v0.1 落地 5 条）

`src/rules.ts` 的实际实现，按顺序短路，第一条命中即返回：

| # | 判据 | 判定 | 播报 |
|---|---|---|---|
| 1 | 进程还没结束，但 `nvidia-smi` 读不到 | `suspect` | `显卡这一刻读不到，可能是外接卡断联` |
| 2 | 退出码 = 0 / ≠ 0 | `ok` / `failed` | `「训练」失败（退出码 137）` |
| 3 | 进程已不在，且超过 30 s 宽限 | `lost` | `「训练」的进程不在了，不是正常退出` |
| 4 | 进程在，静默 > 600 s | `stalled` | `「训练」已经 22 分钟没有输出了` |
| 5 | 进程在，静默 > 180 s | `slow` | `「训练」6 分钟没有新输出` |

三个阈值集中在 `THRESHOLDS`：`slowSec 180`、`stalledSec 600`、`graceSec 30`。
7 个状态全部可渲染：`ok / slow / stalled / suspect / failed / lost / unknown`，优先级 `lost > failed > stalled > suspect > slow > ok`，`unknown` 兜底。

**故意不做的判定**（需要真机数据才敢上，列入 v0.2）：

- 显存单调增长判泄漏——Windows 拿不到 per-process 显存，卡级增长会被别的进程污染。
- `GPU util < 2%` 判空占用——需要连续采样历史，v0.1 不存采样。
- 温度 / 降频判过热——进 `doctor` 自检，不进实时判定。
- 日志里匹配 `CUDA out of memory` / `loss = nan`——需要读日志尾部，v0.2 的适配器一起做。

宁可漏报也别狼来了。规则条数不是 KPI，「播报可信」才是。

### 4.4 通知渠道（v0.2，v0.1 没有）

1. **Windows 托盘气泡**：零配置，本机可见。
2. **ntfy**：手机推送，用户填一个 topic 名，无需账号。
3. **Webhook**：给企业微信/飞书/自建。

去重：同一任务同一判定 30 分钟内只推一次；`ok → 异常 → ok` 恢复也推一条（"训练恢复"）。

## 5. 信息架构与面板

### 5.1 只有一个主视图：任务

```
gpulease · 2 张卡 · 3 个任务                      20:41
────────────────────────────────────────────────
显卡
  卡0 RTX 4090     62%   18.2/24.0 GB   71°C   74 W
  卡1 RTX 3060     88%    9.1/12.0 GB   64°C   92 W

任务
  ● 训练 SDXL LoRA   正常    已跑 1h 12m   最后输出 4s 前
  ● ComfyUI 批量     偏慢    已跑 28m      最后输出 6m 前
  ○ 下载模型         卡住    已跑 51m      最后输出 22m 前

  外部进程 2 个（非本机托管，不猜归属）
```

- 只有两块：**显卡** 和 **任务**。异常任务置顶。
- 卡信息折叠成一行，不让 GPU 抢主体地位。
- 不显示：历史曲线、进程 pid、驱动版本、UUID（诊断页才给）。
- 终端 `watch` 和网页 `/` 是同一份数据、同一套文案，两个入口不说两种话。

### 5.2 交互

v0.1 面板**只读**：没有结束任务、没有调优先级、没有确认告警——`src/server.ts` 只注册了 `GET /`、`/api/state`、`/api/doctor`、`/api/events`。

后续按顺序加，每个都要先有对应的写接口：

| 交互 | 版本 | 依赖 |
|---|---|---|
| 查看日志尾部 | v0.1（CLI 打印路径） | `run --log` 已落盘 |
| 结束任务 | v0.3 | `POST /api/tasks/:id/stop` + 二次确认 |
| 暂停/恢复播报 | v0.2 | 告警层 |
| 调优先级 | v0.5 | 租约与排队 |

## 6. 形态与交付

### 6.1 第一版：一个 exe，三种看法

同一个 `gpulease.exe`，不装服务、不装运行时、不开窗口：

| 形态 | 怎么用 | 状态 |
|---|---|---|
| 终端面板 | `gpulease watch`（2 s 刷新，`q` 退出，`--fast` 1 s） | v0.1 |
| 单页面板 | `gpulease serve` → `http://127.0.0.1:7788`，内嵌 HTML + SSE | v0.1 |
| 托盘气泡 | 双击 exe 起托盘，异常时冒泡 | v0.2 |

**明确不做桌面窗口**：不要 Electron、不要 Tauri、不要第二个浏览器内核。面板就是一屏，浏览器和终端各一份都够；多一个窗口只是多一个要维护的渲染栈。

CLI 全貌（`src/main.ts` 的 `HELP`）：

```
gpulease run --name 训练 [--gpu 0] [--log FILE] -- python train.py
gpulease ls [--json]
gpulease watch [--fast] [--no-color]
gpulease serve [--port 7788] [--host 127.0.0.1]
gpulease doctor [--json] [--bundle]
gpulease --version
```

### 6.2 为什么 exe 而不是 DSH 插件

DSH 插件好用但不是入口：调度器必须独立于 DSH 进程存在（多开会打架），而且用户群（生图/训练的人）大半不用 DSH。
**exe 是产品本体，DSH 插件是 v1.5 的适配层**（复用同一套 HTTP 接口）。

### 6.3 关于 GitHub Actions 出包

**只有一个产物**：`gpulease-win-x64.exe`。在自托管 Windows 节点 `regrevia-win-runner` 上编译 + 冒烟 + 算 `SHA256SUMS.txt`，tag 触发发到 Releases。不接 `pull_request`，不构建第二个平台。
未签名 exe 会被 SmartScreen 拦一次，文档里写清"更多信息 → 仍要运行"，签名留到有人用时再说。

## 7. 版本路线

| 版本 | 内容 | 判定标准（做完能回答什么） |
|---|---|---|
| **0.1.0（已完成）** | 托管启动 `run`、`ls`/`watch`/`serve`/`doctor`、pid 归属、7 状态判定、SQLite 落库 | "现在哪张卡在干什么" |
| **v0.2** | 进度适配器、托盘 + ntfy 告警、按卡归属（NVML）、常驻采集 | "它还正常吗，出事叫我" |
| **v0.3** | attach 外部进程、空占用检测、面板写操作（结束任务） | "这个不是我启动的，能用吗" |
| **v0.5** | 租约 + 等待队列 + 空占用回收 | "两张卡怎么排" |
| **v1.0** | 自动起停 ComfyUI/训练器 + 断联迁移 + DSH 插件 | "卡满了自动换卡" |

**0.1.0 的目标不是功能齐全，是让人第一次看见"原来这是我的训练在跑"。**

## 8. 差异化总结（对着竞品说一句话）

| 竞品 | 它的强项 | 我们不同 |
|---|---|---|
| nvitop / nvtop | 进程级细节、交互极强 | 我们不展示进程，展示任务；它不解释、不告警；nvtop 在 Windows 上不在场 |
| 任务管理器 GPU 列 | 系统自带、零安装 | 它只说 `python.exe`，没有任务名、没有输出活跃度、没有结论 |
| Grafana + dcgm-exporter | 历史、告警、企业级 | 那套只跑 Linux，Windows 上要装 4 个服务才有第一张图；我们一个 exe |
| ComfyUI Manager | 管模型和节点 | 不管 GPU，也不管卡外的任务 |

**一句话：别人给仪表盘，我们给值班员。**

## 9. 待验证假设

1. Windows 消费卡上 `--query-compute-apps=used_memory` 恒为 N/A —— 文档已确认，**待真机复现**（见 `research/windows-and-packaging.md`）。
2. 打包体积：实测定为 exe 109.9 MB / zip 52.2 MB，Node SEA 排除 —— **已决**。
3. 训练进度在没有日志格式约定时，兜底"最后输出时间"够不够用 → 用真实训练脚本试。
4. 用户愿不愿意用 `gpulease run` 包装命令（而不是裸跑）→ 决定 attach 的优先级。
5. 一台机器上 pid → 卡号能不能靠 NVML 稳定拿到 → v0.2 的前置条件，需真机。
