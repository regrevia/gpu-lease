# 产品设计：GPU 值班员（暂名 `gpulease`）

> 一句话：显卡上跑着十来个 `python`，你只想知道「现在在干什么、还活着吗、要不要人管」。
> 这不是监控工具，这是一个会说话的调度台。

---

## 1. 产品命题

### 1.1 用户真正的问题只有三个

| 用户会问 | 现在的答案 | 我们给的答案 |
|---|---|---|
| 这张卡现在是给谁干活的？ | 任务管理器里一堆 `python.exe`，pid 对不上任何东西 | `训练 SDXL LoRA · 卡0 · 62% · epoch 7/30` |
| 它还在正常推进吗？ | 要人去翻日志、看 loss、看 nvidia-smi | `正常，比上轮快 4%，预计 2 小时 10 分` |
| 出事了我怎么知道？ | 出事之后才发现，晚上睡觉跑废了 6 小时 | 手机推送：`20:41 训练停滞 15 分钟，显存仍占 18G` |

### 1.2 为什么不是又一个 nvidia-smi 皮肤

已有的监控（nvitop / gpustat / 任务管理器 GPU 列）解决的是**数值可见性**：利用率多少、显存多少、温度多少。
但用户看到的是一张卡 + 一堆 pid。**数值过剩，语义为零。**

真正的缺口在两层：

1. **归属层**：pid → 人话任务名。需要调度器自己持有进程生命周期（spawn 时注入 `task_id`），以及对外部进程的"纳入管理"（attach）。
2. **判定层**：把时序数值压成一个结论（正常 / 变慢 / 停滞 / 异常），再用一句人话说出来，并决定要不要叫醒人。

**这是产品壁垒，不是 UI 壁垒。** 竞品都能把数字画得更好看，但没人愿意为"更好看的数字"付钱；"半夜别白跑"是愿意付钱的。

### 1.3 不做的事（v1 明确排除）

- 不做全网/多机（v1 单机；多机是 v2 的付费点）
- 不画 GPU 历史曲线（默认不画，展开才有；曲线是 nvitop 的活）
- 不替代 TensorBoard / wandb（只读它们产出的日志，不重做实验跟踪）
- 不自动杀进程、不自动抢卡（v1 只报告 + 建议；自动调度是 v2，需要用户建立信任）
- 不碰集显 / 非 NVIDIA 卡（v1 只认 NVML 能枚举到的）

## 2. 用户与场景

### 2.1 三类人，同一台机器

| 角色 | 场景 | 他关心的 |
|---|---|---|
| 单机炼丹的开发者 | 一张 4090 + 一张 3060，白天训练晚上生图 | 别互相挤爆显存；训练挂了要知道 |
| 小团队共用工作站 | 3 个人 SSH/RDP 上来跑任务 | 现在谁在占卡、我的任务排到第几 |
| 生图/生视频批量跑 | ComfyUI 队列几百张，跑一整夜 | 队列进度、卡死没有、出图失败率 |

三类人的共同点：**卡不是问题，卡上的黑盒才是问题。**

### 2.2 典型痛点，按真实频率排序

1. 训练 OOM 静默退出，人在睡觉（最贵）
2. 两个任务抢同一张卡，互相把对方挤 OOM
3. ComfyUI 卡在某个节点不动，但进程还在、显存还占着（"空占用"）
4. 外接显卡拔了/驱动崩了，任务全死，没人知道为什么
5. 想知道"还要多久"，只能靠眼睛估

## 3. 核心概念

```
Machine ── GPU ×N
              │
              └─ Lease（租约）── Task（任务）── Run（一次执行）
                                    │
                                    ├─ Progress（进度快照）
                                    ├─ Verdict（健康判定）── Alert（通知）
                                    └─ Logs（日志尾部）
```

| 概念 | 定义 | 为什么要它 |
|---|---|---|
| **Task** | 用户视角的最小单位，有**自然语言名字**（"训练 SDXL LoRA"），有类型（训练/生成/服务/下载/批量） | 这是产品的主角，不是 GPU |
| **Lease** | 任务对某张卡的独占占用权，记录 pid 集合、开始时间、可驱逐性、心跳 | 判断"空占用"和"谁在抢"的唯一依据 |
| **Run** | 一次执行（重启 = 新 run），保留历史 | 断联重跑后能说"这是第 2 次尝试" |
| **Progress** | `{phase, done, total, unit, rate, eta}` 的统一结构 | 所有 UI 和播报都吃这一份 |
| **Verdict** | 规则引擎的结论：`ok / slow / stalled / suspect / failed / lost` + 一句人话 | 产品的核心资产 |
| **Alert** | 需要人处理的 Verdict，带去重和静默窗口 | 不打扰是功能 |

### 3.1 三种任务来源

| 来源 | 归属精度 | 怎么做 |
|---|---|---|
| **托管启动**（推荐） | 精确 | `gpulease run --name "训练 SDXL" --gpu 0 -- python train.py`，pid 是自己 spawn 的 |
| **纳入管理**（attach） | 高 | 用户在面板上点"这是训练"，或 `gpulease attach <pid> --name "..."`；读命令行 + 日志目录推断类型 |
| **只读发现** | 低 | 外部进程（别人的 jupyter、系统占用），只显示 `python.exe · 占用 18G · 非本机托管`，不猜 |

**关键设计**：托管启动时把 `GPULEASE_TASK_ID` / `GPULEASE_RUN_ID` 注入环境变量，子进程树全部可追溯；任务退出后由 supervise 进程捕获退出码、回收日志、落库。这比轮询 nvidia-smi 猜 pid 可靠一个数量级。

### 3.2 平台差异（调研结论，直接改写了规则设计）

**Windows 上拿不到「每个进程用了多少显存」。** WDDM 驱动模型下显存由内核统一管理，NVIDIA 驱动不知道单进程占用：`nvidia-smi --query-compute-apps=used_memory` 在 Windows 消费卡上**恒为 N/A**（不是某代驱动的 bug，新一代驱动只是把提示改成 "Not available in WDDM driver model"）。任务管理器的「专用 GPU 内存」列能人工看，但程序化路径（GPU Process Memory 计数器）有微软官方记录的读数不准问题。

后果，决定了 v0.1 必须这么做：

| 平台 | 能做什么 | 规则设计 |
|---|---|---|
| **Linux**（含 WSL2 内跑训练） | per-process 显存可读 | 共享卡也能做"谁占了多少"、精确的显存泄漏判定 |
| **Windows** | 只有 pid + 进程名 + 整卡总量 | 任务级判定只用**进程存活 + 进度 + 日志活跃度**；显存只在卡级说 |

所以规则表里凡是带 GB 数字的，Windows 上要么降级成卡级措辞（"卡 0 显存已满"），要么不显示具体数值。**这不是妥协，是正确性**：宁可说"卡满了"也不要说错"你的任务占了 18.2G"。

另外两条平台事实：Windows 没有 Xid（那是 Linux 内核 NVRM 的概念），等价物是 `nvlddmkm` 事件与 TDR（事件 4101）；DCGM 官方只支持 Linux，所以健康判定不能指望它，得自己按平台写两套信号源。

## 4. 自然语言播报（产品的脸）

### 4.1 三种粒度

**任务行**（面板主体，一行一个任务）：
```
训练 SDXL LoRA  卡0 62%  epoch 7/30  预计 2h10m  正常
```
**卡片**（顶部每卡一行，永远只有 4 个数字）：
```
卡0 RTX 4090  62%  18.2/24G  71°
```
**播报**（异常时的一句话，也是推送正文）：
```
20:41 训练 SDXL LoRA 停滞：15 分钟没有新进度，显存仍占 18.2G。建议查看日志尾部。
```

### 4.2 播报生成原则

- **模板生成，不调 LLM**：离线、免费、确定、0 延迟。规则表 → 句子片段 → 拼装。
- **一句话里必须有**：时间、任务名、现象、可执行的下一步。
- **不做形容词**：不写"运行良好"，写"比上轮快 4%"。
- **异常优先于全面**：正常时少说话（每天最多一条汇总），异常时立即说。

### 4.3 健康判定规则表（核心资产，v1 落地 12 条）

| # | 判据 | 判定 | 播报 | 默认 |
|---|---|---|---|---|
| 1 | 进程退出码 ≠ 0 | `failed` | `退出码 137，通常是显存不足` | 开 |
| 2 | 显存占用单调增长且无回落 > 10 分钟 | `suspect` | `显存从 8G 涨到 21G，疑似泄漏` | 开 |
| 3 | 速度比历史中位数低 70% 持续 5 分钟 | `slow` | `出图从 2.1s/张 降到 9s/张` | 开 |
| 4 | 无任何进度/日志输出 > 15 分钟，进程存活 | `stalled` | `15 分钟没有新进度，进程仍在` | 开（阈值可调） |
| 5 | GPU util < 2% 且占显存 > 10 分钟 | `idle-hold` | `占着 18G 显存但 12 分钟没动` | 开 |
| 6 | 温度 > 85°C 或 throttle reason 非 0 | `hot` | `卡0 过热降频，速度已受影响` | 开 |
| 7 | UUID 从枚举里消失 / 查询超时 | `lost` | `卡1 断联，任务已停止` | 开 |
| 8 | 日志出现 `CUDA out of memory` | `failed` | `显存不足，需要更大卡或降 batch` | 开 |
| 9 | loss 出现 `nan`/`inf` | `failed` | `loss 变成 NaN，训练已无意义` | 训练类默认开 |
| 10 | 队列空但进程挂起 > 30 分钟 | `idle-hold` | `ComfyUI 队列已空，实例仍占卡` | 开 |
| 11 | 磁盘写满（日志/模型目录） | `suspect` | `磁盘剩余 1.2G，训练即将失败` | 开 |
| 12 | 进程树里有僵尸子进程 / 父进程已死 | `suspect` | `父进程已退出，残留 3 个子进程占卡` | 开 |

阈值全部配置文件可调，默认**故意保守**（宁可漏报也别狼来了）。

**平台降级**：#2 和 #5 依赖 per-process 显存，只在 Linux 成立；Windows 上改为「卡级显存饱和 + 进程无进度」的组合判定，播报里不出现具体 GB。

### 4.4 通知渠道（按接入成本排序）

1. **Windows 托盘气泡**：零配置，本机可见（已装 exe 就有）
2. **ntfy**：手机推送，用户填一个 topic 名即可，无需账号
3. **Webhook**：给企业微信/飞书/自建
4. 邮件（v2）

去重：同一任务同一判定 30 分钟内只推一次；`ok → 异常 → ok` 恢复也推一条（"训练恢复"）。

## 5. 信息架构与面板

### 5.1 只有一个主视图：任务

```
┌─────────────────────────────────────────────┐
│ 3 个任务 · 总进度 41%           [暂停播报]   │
├─────────────────────────────────────────────┤
│ 训练 SDXL LoRA   卡0 62%  epoch 7/30  2h10m │
│   ▓▓▓▓▓░░░░░░  正常                          │
│                                             │
│ ComfyUI 批量    卡1 88%  完成 214/500  28m  │
│   ▓▓▓▓▓▓▓▓░░  正常                          │
│                                             │
│ ⚠ 下载模型      卡0 --   停滞 15 分钟        │
│   18.2G 仍占用 · 查看日志 · 结束任务          │
├─────────────────────────────────────────────┤
│ 卡0 RTX4090  62% 18.2/24G 71°               │
│ 卡1 RTX3060  88%  9.1/12G 64°               │
│ 队列 1：推理服务（等 ≥20G 卡）               │
└─────────────────────────────────────────────┘
```

- 异常项**置顶**并带动作按钮。
- 卡信息默认折叠成一行，不让 GPU 抢主体地位。
- 单任务时不显示"总进度"（一个任务的进度条就是它自己）。
- 不显示：历史曲线、进程 pid、驱动版本、UUID（诊断页才给）。

### 5.2 交互只保留四个

`结束任务` · `暂停/恢复播报` · `调优先级`（v2）· `查看日志尾部`

## 6. 形态与交付

### 6.1 第一版：一个 exe

`gpulease.exe` 双击 → 托盘图标 + 本地 Web UI（默认浏览器打开 `127.0.0.1:7788`）。

同一个 exe 兼做 CLI（体积为零成本，且让开发者和 CI 直接用）：

```
gpulease run --name "训练 SDXL LoRA" --gpu 0 -- python train.py ...
gpulease attach 12345 --name "生图批量"
gpulease ls            # 一行一个任务（给人看的自然语言）
gpulease status        # JSON（给脚本）
gpulease serve         # 只跑看板，不开浏览器
gpulease doctor        # 自检：驱动、nvidia-smi、权限、外接卡
```

### 6.2 为什么 exe 而不是 DSH 插件

DSH 插件是好用但不是入口：调度器必须独立于 DSH 进程存在（多开会打架），而且用户群（生图/训练的人）大半不用 DSH。
**exe 是产品本体，DSH 插件是 v1.5 的适配层**（300 行，复用同一套 HTTP 接口）。

### 6.3 关于 GitHub Actions 出包

`windows-latest` 上构建 + 上传产物即可；一个 workflow 出 `gpulease-win-x64.exe`，另一个出 `linux-x64` 二进制。未签名 exe 会被 SmartScreen 拦一次，文档里写清"更多信息 → 仍要运行"，签名留到有人用时再说。

## 7. 版本路线

| 版本 | 内容 | 判定标准（做完能回答什么） |
|---|---|---|
| **v0.1** | 采集 + 托管启动 + 任务列表 + 一条自然语言摘要 | "现在哪张卡在干什么" |
| **v0.2** | 进度适配器（训练/ComfyUI/下载）+ 12 条规则 + 托盘/ntfy 告警 | "它还正常吗，出事叫我" |
| **v0.3** | attach 外部进程 + 空占用检测 + 诊断页 | "这个不是我启动的，能用吗" |
| **v0.5** | 租约 + 等待队列 + 多任务排队 | "两张卡怎么排" |
| **v1.0** | 自动起停 ComfyUI/训练器 + 断联迁移 + DSH 插件 | "卡满了自动换卡" |
| **v2** | 多机（一台看所有机器）+ 团队共享 | 小团队付费点 |

**v0.1 的目标不是功能齐全，是让人第一次看见"原来这是我的训练在跑"。**

## 8. 差异化总结（对着竞品说一句话）

| 竞品 | 它的强项 | 我们不同 |
|---|---|---|
| nvitop / nvtop | 进程级细节、交互极强 | 我们不展示进程，展示任务；它不解释、不告警 |
| 任务管理器 GPU 列 | 系统自带、零安装 | 它只说 `python.exe`，没有任务名、没有进度、没有历史 |
| Grafana + dcgm-exporter | 历史、告警、企业级 | 4 个服务 + Linux 限定；我们一个 exe |
| SkyPilot / dstack | 真编排、多云 | 云原生、Windows 不支持；个人两张卡是过度工程 |
| ComfyUI Manager | 管模型和节点 | 不管 GPU，也不管卡外的任务 |

**一句话：别人给仪表盘，我们给值班员。**

## 9. 待验证假设（进 v0.1 前必须打掉的）

1. Windows 上 `nvidia-smi --query-compute-apps` 的 `used_memory` 在消费卡/WDDM 下是否可用 → 见 `research/windows-and-packaging.md`
2. 打包方案（Node SEA / bun compile / Tauri）体积与 native 模块兼容 → 同上
3. 训练进度在没有日志格式约定时，兜底"日志活跃度"够不够用 → 用真实训练脚本试
4. 用户愿不愿意用 `gpulease run` 包装命令（而不是裸跑）→ 决定 attach 的优先级
